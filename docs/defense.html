🛡️ Distributed Defense & Cloud Security
Module 4 • Zero-Trust

As a public-facing, real-time cloud-native mobile system handling monetary balances and team access, ClubLedger enforces a 5-Layer Defense-in-Depth Architecture.

This protects production workloads against volumetric DDoS floods, bot swarm credential stuffing, short-code brute force, replay attacks, database tampering, and runaway cloud billing exploitation ("Denial of Wallet").

🔍 Deep Dive: The 5 Defense Layers

🌐

Layer 1: Edge & Volumetric DDoS Mitigation (L3/L4 & L7)

Infrastructure Ingestion Protection
Absorbs Ingress Floods

Volumetric attack vectors (SYN floods, UDP amplification, Layer 7 HTTP request storms) are absorbed at the global Anycast edge network (Google Cloud Armor / Cloudflare Edge / AWS Shield) before reaching application compute or triggering Firestore document read billing meters. Unauthenticated edge filtering inspects TLS fingerprints and geographical traffic anomalies.

🔥 Firebase / GCP: Automatically proxied by Google Global Anycast Edge & Google Cloud Armor DDoS protection.
🛠️ Self-Hosted / Ktor: Fronted by Cloudflare Reverse Proxy with Nginx limit_req_zone and Fail2Ban kernel blocks.
📱

Layer 2: Cryptographic Device Attestation (Anti-Bot & Anti-Emulator)

Hardware Proof-of-Origin
Blocks Headless Scripts

Adversaries often deploy automated Python curl scripts or headless emulator farms to scrape member directories or flood invite codes. ClubLedger integrates Hardware Device Attestation (Google Play Integrity API via Firebase App Check).

Every network request carries a cryptographically signed token generated by the device's secure hardware enclave, proving the request originates from an authentic, untampered Android APK installed on certified hardware.

🔑

Layer 3: Sybil & Short-Code Brute Force Prevention

Rate Limiting & Idempotency Keys
Rate Throttled

Team invite codes and join links must resist automated enumeration. Simultaneously, mobile network instability can trigger duplicated payments or double-counted attendance records. ClubLedger solves this via SecurityDefenseHelper:

  • Sliding-Window Rate Limiter: Enforces a maximum of 10 code lookups per 60-second window per client action key, returning RateLimitResult.Throttled if exceeded.
  • Input Sanitization: Strips invalid characters via [^A-Z0-9_-] and forces uppercase formatting to neutralize injection payloads.
  • Deterministic Compound Idempotency Keys: Payments use pay_${userId}_${amount}_${paymentDate}_${method} and attendance uses att_${userId}_${teamId}_${sessionDate}_${sessionType}. Multiple rapid taps or retry storms collapse into a single database record.
🔒

Layer 4: Server-Side Zero-Trust Database ACL & Schema Enforcement

Zero-Trust Firestore ACL
Immutable Ledger Trees

Even if a malicious user inspects or modifies client bytecode, cloud databases reject unauthorized state mutations. ClubLedger enforces comprehensive firestore.rules:

  • Strict Authentication: All club subcollections require authenticated sessions (request.auth != null).
  • Immutable Append-Only Trees: Root clubs, user records, teams, budgets, and ledger items reject deletes (allow delete: if false;).
  • Schema Type Validation: Ensures numeric and string constraints (e.g., amount is number, runningBalanceAfter is number) are validated at the cloud firewall before entering storage.
💰

Layer 5: Financial Defense & "Denial of Wallet" Hard Caps

Cost Shield & Circuit Breakers
Zero-Shock Billing

Malicious bot swarms can induce "Denial of Wallet" by firing millions of repeated read requests against pay-per-read NoSQL databases. ClubLedger guards against financial depletion through three shields:

🗄️ Offline-First Caching

Local Room SQLite database serves all UI queries. Remote reads only execute on deliberate sync triggers or cache misses.

⏱️ Reactive Debouncing

Kotlin Coroutines debounce(300ms) prevents rapid keystroke emissions from triggering successive backend query storms.

🛑 Budget Circuit Breakers

Google Cloud billing alerts with Pub/Sub Cloud Functions automatically disable billing or cap API thresholds upon budget overrun.

// 1. Sliding Window Rate Limiter
fun checkRateLimit(
    actionKey: String = "join_team_code",
    maxRequests: Int = 10,
    windowMs: Long = 60_000L
): RateLimitResult {
    val now = System.currentTimeMillis()
    val timestamps = actionTimestamps.getOrPut(actionKey) { mutableListOf() }
    timestamps.removeAll { now - it > windowMs }

    return if (timestamps.size < maxRequests) {
        timestamps.add(now)
        RateLimitResult.Allowed(maxRequests - timestamps.size)
    } else {
        val oldest = timestamps.firstOrNull() ?: now
        val wait = (((oldest + windowMs) - now) / 1000).coerceAtLeast(1)
        RateLimitResult.Throttled(retryAfterSeconds = wait)
    }
}

// 2. Deterministic Compound Idempotency Key
fun createIdempotentPaymentKey(
    userId: Long, amount: Double,
    paymentDate: Long, method: String
): String = "pay_${userId}_${amount}_${paymentDate}_${method.trim().uppercase()}"
firestore.rules Cloud Database ACL 
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    match /clubs/{clubId} {
      allow get, list: if request.auth != null;
      allow delete: if false; // Tree never deleted from client

      // Immutable append-only ledger sub-collection
      match /ledger/{ledgerId} {
        allow read: if request.auth != null;
        allow create, update: if request.auth != null
          && request.resource.data.userId is number
          && request.resource.data.amount is number
          && request.resource.data.runningBalanceAfter is number
          && request.resource.data.createdAt is number;
        allow delete: if false; // Deletions strictly forbidden
      }

      // Payments sub-collection
      match /payments/{paymentId} {
        allow read: if request.auth != null;
        allow create, update: if request.auth != null
          && request.resource.data.amount is number
          && request.resource.data.status is string;
        allow delete: if request.auth != null;
      }
    }
  }
}

⚖️ Financial Governance & Access Control Policies

👑

Superset Role Hierarchy

Global Admin > Team Admin > Captain > Member. Admins inherit all member privileges plus audit dashboards, dispute adjudication, and treasury controls.

🔒

Two-Man Rule Verification

Member-logged payments require explicit Treasurer or Team Admin verification and approval before entering the verified treasury balance.

📝

Immutable Transaction Logs

Balances are append-only. No user can rewrite balances without an explicit debit/credit entry accompanied by a mandatory audit reason.

⚖️

Built-in Dispute Mediation

Formal dispute workflows allow players to contest attendance records or fee invoices. Resolution generates an automated compensating ledger record.

🔑

Granular Team Permissions

Team Admins can only view and manage rosters and budgets designated to their specific team; cross-tenant leakage is strictly prevented.

🗄️

Room Migration Safety

Room schema migrations (v1 ➔ v2) utilize safe column alterations with backward compatibility and zero data loss on app upgrades.

🛡️
Security & Audit Assertion

Historical financial transactions cannot be deleted by any user or team admin. All accounting records remain permanently verifiable for Annual General Meetings (AGM), tax filing, and formal financial auditing.
